addon.json

The Aefos addon format

Aefos installs one bundle format, and this is it. A bundle is a folder with a manifest and whatever artifacts it carries. Anything packaged for another ecosystem is converted to this once, when it is authored — ask an agent, with the button above.

The bundle

<slug>/
  addon.json          REQUIRED - the manifest below
  command/
    COMMAND.md        one command, triggered as /<slug>
  skill/
    SKILL.md          one skill
    okf/              its knowledge bundle (index.md, ...)
  mcp/
    server.json       one mcpServers fragment
  tools/              Python tools
  templates/          scaffolds the command or skill renders

The manifest

{
  "slug": "janus-orm",
  "version": "1.0.1",
  "name": "Janus ORM Specialist",
  "description": "Expert on the Janus ORM.",
  "trust": "community",
  "requirements": { "aefos_version": ">=1.0.0" },
  "artifacts": {
    "command": true, "skill": true,
    "mcp": false, "tools": false, "templates": false
  }
}

slug and version are required and must match the store entry. artifacts declares what the bundle carries: declared and missing fails the install, so a no-op is never recorded as success.

More than one command or skill

Use the plural folder — a directory per artifact, not a loose file:

<slug>/
  commands/
    build/COMMAND.md        -> /<slug>.build
    review/COMMAND.md       -> /<slug>.review
  skills/
    test-runner/SKILL.md
    lint/SKILL.md
in the bundleinstalls totrigger
command/COMMAND.mdcommands/<slug>//<slug>
commands/<name>/commands/<slug>.<name>//<slug>.<name>
skill/skills/<slug>/—
skills/<name>/skills/<slug>.<name>/—

The <slug>. prefix is not decoration: commands and skills share one flat root, so two addons both shipping a review would otherwise overwrite each other.

What install does

  • Everything lands under ~/.aefos, scoped to the slug.
  • A reinstall clean-replaces: an artifact the new version dropped is gone, not left behind still loaded.
  • mcp and tools are runnable code. From a community-trust store they need explicit consent (--yes).
  • Over HTTP a bundle without a sha256 is refused.

Publishing it

A folder store needs no packaging at all: point a store at a directory and every subfolder carrying an addon.json is an addon.

aefos sources add mystore --kind path --location D:\Addons
aefos install my-addon --source mystore
Aefos addon format (addon.json)

A bundle is a folder with a manifest:

  <slug>/
    addon.json          REQUIRED
    command/COMMAND.md  one command, triggered as /<slug>
    skill/SKILL.md      one skill (+ okf/ for its knowledge bundle)
    mcp/server.json     one mcpServers fragment
    tools/              Python tools
    templates/          scaffolds

addon.json:

  {
    "slug": "my-addon",
    "version": "1.0.0",
    "name": "My Addon",
    "description": "What it does.",
    "trust": "community",
    "requirements": { "aefos_version": ">=1.0.0" },
    "artifacts": { "command": true, "skill": true,
                   "mcp": false, "tools": false, "templates": false }
  }

slug and version are required and must match the store entry. artifacts
declares what the bundle carries; declared and missing fails the install.

For several commands or skills, use the plural folder - a DIRECTORY per
artifact, never a loose .md:

  commands/build/COMMAND.md   installs as /<slug>.build
  commands/review/COMMAND.md  installs as /<slug>.review
  skills/test-runner/SKILL.md installs as skills/<slug>.test-runner

The <slug>. prefix is required: commands and skills share one flat root,
so two addons both shipping "review" would otherwise overwrite each other.

Install rules:
- everything lands under ~/.aefos, scoped to the slug
- a reinstall clean-replaces; a dropped artifact is removed
- mcp and tools are runnable code: community-trust needs --yes
- over HTTP, a bundle without sha256 is refused

To publish without packaging, point a store at a folder:
  aefos sources add mystore --kind path --location D:\Addons
  aefos install my-addon --source mystore
